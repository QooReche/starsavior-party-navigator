# 탐색 실행기 1단계

## 동결 기준

`6688d7a`에서 `tests/search_freeze_test.js --capture`로 생성했음. 합성 계정만 사용함. `tests/fixtures/search_execution_6688d7a.json.gz`는 전체 JSON을 gzip으로 보관함. 객체 키와 전송 식별자만 정규화하며 배열 순서·중복은 보존함. 단계별 작업에는 승격·학습 감사·복귀 후보와 판 수·시드·실행 배치가 포함됨.

- 코스모: 학습 선별, 자동 난이도, 브레이크, 3팀 최종 순서.
- 코스모 전송 보완: `search_cosmo_trace_test.js`는 불변 `6688d7a`의 합성 실행 함수를 사용하고 같은 커밋의 모듈에서 골든을 생성함. 공통 의존성이 바뀌면 재생성을 막음. 실제 `postMessage` 전체와 최종 결과를 보관하여 단계·기본 URL·옵션·배치 경계·전송 순서를 비교함. 전송 경로에 단계/옵션/팀 순서/시드 변이를 넣고 탐색을 다시 실행하여 4개 모두 검출했음.
- 길드: 큰 풀·작은 풀, 협공 제외 켬/끔, 지원, 브레이크, 기본/학습 경로.
- 일반 추천: 실제 `recoCalculate`·`recoEvaluate`의 2파티 순차 실행과 캐시 재사용. 후보 생성은 합성 스냅숏이며 기존 `reco_reuse_test`가 실제 후보 생성 순서를 별도 검사함.
- 일반 예선 보완: `tests/search_screen_freeze_test.js`는 불변 커밋 `6688d7a`의 실제 페이지/런타임에서 별도 골든을 생성했음. 5후보의 8판 → raw를 돌려보내 24판 추가 → 32판 승격/최종 순서를 비교하며 판 번호 초기화 변이를 검출함.
- 직접 실행: 실제 `directRunRows`의 요청·결과·캐시 재사용.
- 결과 원문: `raw/t60/ci/progs/via/unsupported`를 포함한 런타임 응답을 보관함. 길드의 기존 결과 투영은 변경하지 않음.
- 실제 Pyodide: `tests/e2e/test_search_executor.py`, 표준 육성 4명·달 회랑 FLOOR 100·2판·고정 시드. 요청·원문 결과·투영 결과와 양수 진행도를 비교함. 엔진 입력은 아래 «실제 Pyodide 엔진 입력 고정»대로 `6688d7a` 판을 공급함.

취소·재개·우선순위·오래된 응답·가상 시계 ETA·비중복 실패·확대 복귀·배치 스위치는 기존 개별 시험도 계속 실행함. 모든 조합을 하나의 골든으로 포괄한다고 간주하지 않음.

## 실제 Pyodide 엔진 입력 고정 (11/22)

11/21 엔진 규칙(`battlesim/rules/default.json` 등)을 클라 기준으로 여러 번 고쳐 «현재 엔진 = `6688d7a` 엔진» 단언이 깨졌음. 이 시험의 목적은 실행기 리팩터 동등성이지 엔진 동결이 아님. 그래서 고정 대상을 «현재 저장소 엔진»에서 «워커에 공급하는 엔진 입력»으로 옮겼음.

- 방법: `serve_frozen_engine`이 Playwright 경로 가로채기로 워커의 `sim/manifest.json`과 manifest 파일(`?v=<6688d7a ver>`)을 `git show 6688d7a:` 원본으로 응답함. 페이지·실행기(`search_executor.js`·`guild_search.js`)는 현재 판을 그대로 씀.
- 보호 장치: fixture의 `pins` 해시가 `6688d7a` 원본과 같은지, 로더인 `sim_worker.js`가 `6688d7a`와 바이트 동일한지, 워커가 manifest와 모든 엔진 파일을 고정본으로 받았는지 확인함. 응답 `ver`도 고정본 ver와 같아야 함(`comparison_payload`).
- 기준선 재생성(b안)을 쓰지 않은 이유: 현재 엔진으로 다시 만들면 기준선이 리팩터 뒤 코드로 생성되어 «리팩터 전 실행기 결과»라는 근거가 사라짐. 또 규칙을 고칠 때마다 재생성이 필요해짐. a안은 `6688d7a` 실측 fixture를 그대로 두고 엔진 변경과 무관하게 유지됨.
- 한계: `sim_worker.js`(엔진 로더·워커 프로토콜)를 바꾸면 이 시험은 일부러 실패함. 그때는 프로토콜 변경 자체를 별도 검토해야 함.
- 변이 확인: 실행기 시드 +1, 투영 결과 `prog`×0.999, 고정본 대신 현재 엔진 파일 공급 세 가지 모두 실패했음(원복 후 통과).

## 실행기 경계

`search_executor.js`는 워커 생성·보관·종료, 정적/청크 배분, 소유자 대기열, 응답 검증, 진행 콜백, 시간 감시, ETA 계산을 소유함. DOM·콘텐츠 이름·후보 선정·점수식은 알지 못함. 기존 `GuildSearch`·페이지 함수는 호환 래퍼임. 공통 실행 결과는 원문이며 기존 길드 투영은 래퍼에 남겼음.

첫 추출과 풀 자원 관리 통합은 별도 커밋으로 나눴음. `SIMPOOL`과 전용 `workerPool`, 풀 없는 단계도 같은 `workerPool` 자원 소유자를 사용함. 유지 기간은 기존 계약을 따름: 일반/직접 실행은 공유 재사용, 코스모/길드 학습은 탐색 단위 재사용, 길드 기본 경로는 단계 종료 때 종료함. 서로 다른 탐색 스코프를 하나의 전역 대기열로 합치는 정책 변경은 하지 않았음. 따라서 페이지 전체의 동시 워커 수를 하나의 상한으로 제한하는 변경은 아님. 기존 작업 배분·수명과 완전 동일 대조를 우선한 경계이며, 전역 스케줄링은 후속 단계에서 별도 비교가 필요함.

## 작업 묶음(`o.chunk`, 2026-11-22)

`simDispatch`에 `chunk`(기본 1)를 주면 이어진 작업 여러 개(작업 하나 = 팀 하나)를 한 요청으로 보냄. 일반 추천 훑기·예선(`simScreen` `leg`, `recoEvaluate` `screen`)만 `SearchExecutor.chunkSize(팀 수, 작업자 수) = min(50, ceil(팀 수/(작업자×40)))`를 씀. 작업자 8개면 훑기 10,626팀은 34팀씩, 예선 120팀은 1팀씩이라 지금과 같음. 본선·직접 편성·배치 비교·육성은 1팀씩 그대로임. 코스모·길드는 `runPhase`의 `chunk`를 그대로 씀.

- 대여(`lease.keys` = 팀 key → 작업 번호, `lease.got`)는 묶음 안의 key이면서 처음 온 것만 받음. 남의 key와 중복은 버림. `done`은 전부 받았을 때만 인정하고, 아니면 «결과 없이 끝난 작업» 오류를 냄.
- 요청 머리(판 수·옵션·시드 등 `teams` 밖 전부)가 다르거나 key가 겹치면 묶음을 끊음. 다음 작업의 `msg`는 `b.peek`에 두므로 작업마다 한 번만 만듦.
- 무진행 감시와 속도 표본은 팀 단위임. 작업자가 팀마다 «시뮬 i/N팀»을 보내고, `team`마다 `w._last`를 갱신함. 취소는 지금처럼 `terminate`이고, 이미 받은 팀 결과는 남음.
- 작업자(`sim_worker.js`)는 팀이 여럿이면 `battlesim.web.AutoBatch` 하나로 돌림. 조우 정규화와 의미 해석 캐시는 묶음 안에서만 공유함. 결과는 팀별 `run_auto`와 글자 그대로 같음(`tests/batch_identity_test.py`).
- 시험은 `tests/search_executor_batch_test.js`(계약 8건, 변이 5건)임. 진행 표시는 `SearchExecutor.throttle`(`PAINT_MS` 200ms)로 간격을 제한함.

## 길드 시간 측정

`tests/e2e/test_search_executor.py --bench <파일>`로 실제 Pyodide를 사용함. `--legacy`는 `6688d7a`의 길드 실행기·정책 모듈을 같은 페이지에 로드해 교차 대조함.

5명의 고정 합성 능력치, 5조합 → 2팀 → 1팀, 단계 0/2, 지원 없음, 단계당 1판, 브레이크 없음, 워커 2개, 새 브라우저 컨텍스트와 단계별 새 엔진을 사용함. 단계 유휴 시간은 `2 × 단계 경과 시간 − postMessage~done 구간 합`으로 정의함. 준비·전송은 작업 중 시간에 포함하며 CPU 유휴율과는 다름. 팀별 통계나 계정 성능 검증을 위한 자료가 아님.

실제 25분 조건의 전체 탐색은 이 PC의 메모리 제한 때문에 수행하지 않고 축소판의 전후 비율만 판정함. 32.5분을 실제 측정한 것으로 환산하지 않음.

최종 계측은 `tools/measure_guild_executor.py tests/fixtures/guild_executor_cross.json`을 Playwright Python으로 실행했음. 다른 시험을 종료한 뒤 이전→현재→현재→이전 순으로 새 브라우저를 열었음. 위 3단계 조건에 스타피어서 Lv.1·미장착·선택 단계±1의 4단계를 추가했고, 계측용 브레이크 판 수도 1판으로 줄였음. 원래 설정은 실행 뒤 복원함. 정책·후보·판 수를 줄이는 운영 코드 변경은 없음.

| 구분 | 이전 | 현재 |

| 실행 2 (ms) | 8078.6 | 8012.2 |

전후 비율 0.9935로 축소판 1.3배 상한을 통과했음. 각 실행의 최종 결과·설정·엔진 버전을 완전 비교했음. 원문에 구현 소스 해시·단계별 경과/작업 중/유휴 시간을 보관함. 초기 추출 직후 3단계 측정 6052.5→5882.7ms도 별도 fixture로 보존했지만 최종 판단은 위 교차 측정 기준임.

이 표본에서는 엔진 준비가 작업 중 시간에 포함되어 있음. 학습 경로의 팀별 순차 대기나 실제 25분 탐색의 병목을 이 수치로 확정하지 않음. 다음 단계에서 동일 실행기의 측정 경계를 사용해 전체 후보·학습 경로·브레이크 조건별로 다시 재고, 결과를 바꾸지 않는 요청 재사용과 대기 비용부터 조사하기로 함.

## 최종 검증

`COSMO_TABLES`를 이 PC의 추출 표 경로로 지정하여 `python -X utf8 -I tools/run_tests.py --rebuild --strict` 238파일 통과·실패 0·건너뜀 0을 확인했음. 이 실행 시작 뒤 추가한 `search_cosmo_trace_test.js`는 같은 실행기의 `search_cosmo_trace --strict` 선택 실행으로 별도 통과했음. 합계 239파일이며 코스모 전송 경로 변이 4개도 포함함.

브라우저는 `test_cosmo_direct.py`, `test_placement.py`, `test_gwen_search_stage.py`, `test_search_executor.py`와 `test_page.py`의 관련 그룹만 한 번에 하나씩 실행했음. 페이지 관련 그룹은 실제 시뮬/미지원, 자동·수동 판 수, 예선 중단 안내, 코스모 자동 단계/찾기/복귀, 길드 찾기/누락 응답/브레이크/화면 전환, 부분 시간 초과였음. 시간 초과 시험에서 발견한 타이머 회귀는 수정 후 다시 통과했음. 실제 시뮬 워커는 최대 2개로 제한했으며 전체 e2e는 실행하지 않았음.
