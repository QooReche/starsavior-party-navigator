# 코스모 탐색 공통 최적화 확인

## S1 중복 계측

`node tools/bench_cosmo_common.js`로 실제 `CosmoSearch.search`가 작업자에게
보내는 전투 요청을 계측했음. 합성 구원자 13명, 난이도 자동, 브레이크 1종,
축소한 탐색 예산을 사용했음. 계정 자료와 실제 전투 엔진은 사용하지 않았음.

동일성 키는 `[base, stage, seed, n_runs, 공통 options, party, 팀 options]`임.
능력치·육성 상태·리더·배치·규칙·보스·난이도·브레이크·판 구간을 모두 포함함.
작업 식별자와 작업자 번호는 엔진 입력이 아니므로 제외했음
(`sim_worker.js`의 `run(m.stage, party, m.n_runs, m.seed, ex)`).

| 합성 경로 | 육성 전 요청 | 같은 탐색 안 중복 | 1명 HP 변경 후 요청 | 전후 동일 요청 | 전원 HP 변경 후 동일 요청 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 전수 선별 | 2,578 | 0 | 2,578 | 1,819 | 0 |
| 학습 선별 | 429 | 0 | 429 | 330 | 0 |

`growth_ui.js`의 계절 콘텐츠 경로는 육성 전 탐색 뒤
`cosmoSearchStart(state, snapshot.profile)`를 다시 호출함.
육성으로 바뀌지 않은 구원자 네 명의 팀은 전투 입력이 그대로일 수 있음.
S1은 이 전후 중복에 적용함. 탐색 단계 사이는 시드·판 수가 달라
이번 합성 입력에서 완전히 동일한 요청은 없었음. 긴 판 결과를 짧은 판에
대입하거나 다른 시드의 결과를 공유하지 않음.

계측의 가짜 결과는 입력 능력치에도 의존함. 첫 행의 구원자 한 명만
변경하는 경우와 전원 변경하는 경우를 나눠 동일 팀 이름만으로 결과를
공유하는 오류를 확인할 수 있게 했음. 이 수치는 합성 경로의 중복률이며
실제 계정의 절감률을 뜻하지 않음.

## 공통 결과 캐시와 검증

`ScoreSearch.battleCache`가 전투 입력 직렬화와 결과 조회·저장을 맡음.
길드는 기존처럼 육성 전 결과만 저장하고 육성 후 경로에서 조회함.
코스모는 단계별 `run`에서 동일 요청을 조회하고 빠진 작업만 원래 순서로
실행함. 점수 결합·판별 협공 비율·후보 선정은 각 콘텐츠가 계속 맡음.
캐시는 세션의 엔진 버전·데이터 버전 수명 안에서만 사용함.

합성 육성 후 요청은 전수 2,578→759, 학습 429→99로 줄었음.
동일 입력 재실행은 두 경우 모두 추가 요청 0건이었음.
`tests/cosmo_battle_cache_test.js`가 캐시 없는 실행과 전체 결과 및 남은
요청 순서를 비교함. 재사용 중 취소도 확인함. 실제 코드를 바꿔 재사용을
끄거나 키에서 시드·판 수·공통 규칙·파티·팀 옵션을 빼는 여섯 변이가
모두 실패하는지 확인했음.

한 번의 합성 측정에서 학습 경로 동일 입력 재실행은 234.7→181.9 ms였음.
전수 경로는 73.0→132.1 ms, 육성 후 학습 경로는 169.5→191.8 ms였음.
가짜 작업자가 실제 전투를 계산하지 않아서 이 시간에는 학습·키 직렬화·
취소 응답용 이벤트 루프 양보 비용이 주로 포함됨. 실전 전투 시간 절감률의
근거로 쓰지 않음. 위 명령이 현재 환경의 시간과 요청 수를 함께 출력함.

## S2 세션 풀 공통화

`SearchExecutor.createSession`이 풀 유지·버전 변경 시 교체·캐시 초기화·종료를
맡음. 길드의 `GuildDaily.createSession`도 같은 함수를 사용함. 코스모 화면은
클릭마다 `sim/manifest.json`을 새로 확인하고 엔진·데이터·base가 같으면
기존 풀을 다시 씀. 조건만 바꾼 재실행도 작업자를 재생성하지 않음.
일반 다시 찾기는 전투 캐시를 비우고, 이어지는 육성 비교만 같은 캐시를 씀.

각 세션의 작업자 생성 직전 훅과 공용 풀의 `beforeCreateWorker`가 다른
놀던 풀을 회수함. 실행 중인 세션은 보존하고, 코스모의 지역 육성 상태가
공유 중인 풀도 `session.active`로 보호함. 취소·오류·낡은 실행 종료는
해당 세션을 닫되 새 실행의 세션을 건드리지 않음. 페이지 전역이 없는
시험 조각에서도 동작하도록 회수 훅에 `typeof` 가드를 둠.

독립 리뷰에서 전역 풀이 이미 해제된 뒤 육성 비교만 시작하면 지역 상태에
새 풀이 생겨 완료 후 회수할 수 없는 경로를 찾았음. `growthStart`의
`finally`가 지역 상태만 소유한 세션을 닫도록 고쳤음. 실제 육성 호출 경로를
쓰는 `cosmo_growth_session_test`가 수정 전 실패·수정 후 통과했고,
정리 누락과 공유 풀까지 닫는 두 변이를 모두 검출했음.

`cosmo_session_test`는 다시 찾기·조건 변경·엔진만 변경·길드/코스모/공용 풀
전환·생성 직전 경쟁·육성 보호·취소/오류/낡은 실행 정리를 검사하며
10개 변이를 검출함. 길드 S2 시험의 기존 결과 기대값도 유지함.
`search_executor_batch_test`의 daily 변이는 새 생성 훅을 잘못 지우지 않도록
탐색 호출 직전의 trim을 정확히 지정했음. 기존 검사값은 바꾸지 않았음.

`node tools/bench_cosmo_session.js`는 기준 커밋과 현재 화면 호출 경로를
같은 합성 입력으로 각각 예열 1회·측정 5회 실행함. 동일 입력 재실행과
조건 변경 재실행의 작업자 생성 수, 전투 요청 수, 전체 결과를 대조함.
인위적인 작업자 부팅 지연은 넣지 않았으며 브라우저/Pyodide 부팅 시간은
포함하지 않음.

11/28 재개 측정(5회 중앙값): 같은 조건 다시 찾기는 32.474→34.346 ms,
조건 변경은 33.519→33.008 ms였음. 두 경우 모두 새 작업자 수는 1→0,
전투 요청은 113건으로 같았고 전체 결과도 일치했음. 합성 작업자에서는
부팅 비용을 측정하지 않으므로 시간 개선을 입증한 결과로 쓰지 않음.
브라우저 재실행 시간은 별도로 측정하지 않았음.

관련 Node 시험 81파일이 통과했음. 재개 첫 검사 80파일 중 묶음 실행기의
소스 위치 검사 1건이 실패해 호출 직전 trim 순서와 변이 위치를 정리했음.
리뷰 수정 후 영향을 받는 53파일을 다시 실행해 통과했으며 위 수에는 새
육성 세션 시험도 포함함. 코스모 동결값과 길드 S2 기대값은 유지했음.
`test_page.py`의 코스모·길드 15개는 이름 필터 8묶음으로 순차 실행해
모두 통과했음. 매 묶음 시작 전 여유 메모리 6 GiB 이상을 확인했음.
