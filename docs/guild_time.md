### 판 수 의견 — 설정 변경 없음

- 예선 2판의 상위 20%는 최대값 1개임. 2차로 승격한 400팀의 같은 10판 결과에서 앞 2판만 쓰면 상위 12팀이 전체 10판과 7~12팀만 겹쳤음(A 두 시드는 12, E는 11·7). 거친 선별용으로만 쓰고 승격 후보는 10~20판으로 확인하는 안을 제안함. 예선에서 이미 탈락한 팀의 오탈락률은 이번 자료로 확인하지 못했음. 넓은 예선을 일괄 증량하면 비용이 크게 늘어남.
- 같은 결선 후보를 앞 20판과 전체 40판으로 재정렬하면 4탐색 중 3회에서 1위 팀이 바뀌었음. 브레이크 비교는 4회 중 2회였음. 뒤 20판도 대조했고 원래 40판 선택 결과의 재생 일치를 확인했음. 추가 전투는 0판임. **결선·브레이크 40판의 일괄 축소 근거는 없음.** 40판을 유지하고 근접한 상위 후보만 100판으로 확인하는 안을 P3 후보로 제안함. 40판으로 순위가 수렴했다고 주장하지 않음.

현재 30112와 보관 30111(BFB), 기존 측정 계정, 네이티브 Python 작업자 2개로 순차 측정하기로 함. A(현재 기본)와 E(옛 방식 + P.baseline 자리·리더)를 각각 탐색 시드 오프셋 0·100·200으로 새 실행 3회 수행함. 매 탐색 직후 첫 편성을 고정하고 독립 50시드×20판을 평가함. 평가 시드는 탐색 반복별 20270101·20270201·20270301부터이며, 같은 반복의 A/E는 같은 시드를 씀. 다중 출전·합산은 구현 전이므로 1팀만 평가함. D(새 방식 + 배치 확장)는 가능하면 30112·오프셋 0으로 1회 별도 측정함.

지표는 상위 20% 점수 비율, 상한 도달률 차이(%p, 95% 구간), 평균 점수 비율(95% 구간), 클리어율 차이, 탐색 시간 비율(3회 중앙값·최댓값), 총 판 수 비율로 고정함. 상한은 선택 편성·단계의 이론적 최대 점수 도달이며 클리어와 별도 집계함. 품질 구간은 각 탐색 반복을 유지하고 같은 독립 판 번호를 짝지어 재표집하는 percentile bootstrap 4,000회로 계산함. 세 반복의 평가판을 같은 가중치로 합치며, 계정·시즌은 섞지 않음. 구간은 이 세 번의 선택에 조건부이며 탐색 전체의 불확실성을 보장하지 않음.

E 채택은 각 계정·시즌에서 상위 점수 비율 95% 하한 ≥ 0.995, (상한 도달률 차이 95% 하한 > 0 또는 평균 점수 비율 95% 하한 > 1.0), 평균 점수 비율 95% 하한 ≥ 0.98, 중앙 탐색 시간 비율 ≤ 1.1을 모두 만족할 때로 고정함. 결과를 보고 기준을 바꾸지 않으며 기본 스위치는 이번 작업에서 끔을 유지함. D에는 옛 1.3배 제한을 적용하지 않고 관측값만 보고함.

재개·캐시 재사용 실행은 시간 판정에서 제외함. 다른 무거운 작업이 없는 상태를 확인하고 실행 부하를 비공개 로그에 남김. 원문은 기존 비공개 측정 폴더 아래 별도 P0 디렉터리에 보관하고, 공개 문서에는 비율·구간만 기록함. 브라우저 측정·전체 시험·e2e는 하지 않음.

## 측정 조건

`tools/measure_guild_time.js ACCOUNT PRIVATE_DIR old|new [SETTINGS_JSON]`으로 실제 페이지에 실린 시즌·제외 목록·보유 지원 브레이크·계정 능력치를 사용함. 선택 효과는 기본값인 모두 끔, 사용자가 제외한 구원자는 없음, 워커는 최대 2개임. `GuildPlanner` → `GuildSearch` → `SearchExecutor`는 화면과 같으며 전송만 네이티브 Python 엔진으로 바꿈. 브라우저 Pyodide 절대 시간으로 환산하지 않음.

11/20 기록의 새 방식은 배치·리더 확장도 켠 조건이었음. 이번 기준선은 현재 설정에서 `newSearch`만 전환하며, 두 조건을 같은 것으로 취급하지 않음. 저장소의 길드 자료는 종료된 시즌 4이므로 현재 운영 시즌에서 검증했다고 쓰지 않음.

입력 해시·소스 해시·설정·단계·시드·판 수를 고정하고 응답마다 비공개 폴더의 JSONL에 기록함. 같은 폴더로 재실행하면 완료 응답을 재사용하며 입력이나 소스가 달라지면 거부함. 재개한 실행은 `resumed=true`로 표시하고 새 실행의 절대 시간 판정에 사용하지 않음. 단계별 경과·요청 처리 시간·유휴 시간과 단계 사이 간격을 기록함. 유휴는 `2 × 경과 − 요청 전송부터 done까지 합계`이며 CPU 사용률은 아님.

실제 브라우저 시간은 Playwright Python으로 `tools/measure_guild_browser.py ACCOUNT PRIVATE_DIR --new`를 실행함. 같은 계정·시즌·정책에 실제 Pyodide 워커 2개를 사용하고, 새 브라우저 컨텍스트에서 시작함. 이 도구도 응답별 저장·재개를 지원하며 재개한 실행은 시간 판정에서 제외함. 네이티브와 브라우저 결과를 별도로 보고함.

## 독립 재평가

`tools/evaluate_guild_time.js ACCOUNT PRIVATE_DIR SEARCH_DIR ...`로 탐색이 선택한 첫 행을 고정해 평가함. 탐색 시드와 분리한 50개 시드에 각각 20판, 합계 1,000판을 사용함. 진행도마다 점수를 계산하며 상위 20% 평균·전체 평균·클리어율을 따로 기록함. 정책 사이 같은 판 번호를 묶은 percentile bootstrap 4,000회로 점수 비율과 클리어율 차이의 95% 구간을 계산함. 개별 클리어율은 Wilson 구간을 함께 기록함. 같은 편성을 선택하면 같은 판별 결과로 차이 0을 확인할 수 있음.

한 계정·한 번의 탐색은 다른 계정이나 탐색 시드의 품질 보장이 아님. 유의한 차이를 검출하지 못했다는 사실만으로 동등성을 확정하지 않음. 재평가 결과를 보고 다시 후보를 고르면 독립 평가가 아니므로 그런 후보 변경 뒤에는 별도 시드의 새 평가가 필요함.

계정·후보·점수·클리어율 원문과 로그는 저장소 밖 비공개 폴더에만 보관함. 기본 전환은 시간과 독립 평가를 확인한 뒤 별도 커밋으로 다룸.

## 작업 배분 조정

새 방식의 `search.execution.chunk`를 1로 두었음. 기존 묶음 8에서는 정밀 비교 2작업이 한 워커에만 배정되어 해당 단계 유휴가 절반이었음. 짧은 단계의 끝부분도 남은 묶음을 한 워커만 처리했음. 공통 실행기의 기존 동적 대기열로 작업을 하나씩 배분하고 탐색 전체에 같은 두 워커를 재사용함.

후보·학습·감사 확대·판 수·시드·점수식은 바꾸지 않았음. 예선의 소표본은 선별에만 쓰고 기존 독립 시드의 정밀 비교를 유지함. 추가로 선택 결과를 1,000판 holdout으로 검증함. 배치·리더 확장 스위치도 현재 설정을 유지함. 미지정 `chunk`는 이전 값 8로 동작함.

`guild_dispatch_test.js`는 묶음 8/1에서 전체 단계의 작업·시드·판 수·판별 결과·최종 출력을 대조함. 워커 하나·둘, 취소 후 정리, 협공 포함과 양수 진행을 검사함. 실제 배분을 8로 되돌린 변이가 두 워커 사용 단언에서 실패함. 기존 동결 fixture는 바꾸지 않고 `guild_defaults_test.js`에서 당시 묶음 8을 명시함.

## 검증 결과와 전환 판단

같은 입력으로 기존 방식·새 방식 변경 전·후를 각각 한 번 새 실행했음. 네이티브의 변경 후/전 시간 비율은 0.9319였고 전체 최종 결과가 같았음. 정밀 비교 2작업 단계의 합산 유휴 비율은 약 50%에서 0.54%로 줄었음. 큰 후보·감사 단계가 대부분의 시간을 차지하므로 작은 단계의 배분 개선만으로 큰 폭의 단축을 주장하지 않음.

탐색과 분리한 1,000판에서도 새 방식 전후의 판별 점수·클리어 여부가 같았음. 상위 20% 평균과 전체 평균의 비율 및 95% 구간은 모두 1, 클리어율 차이와 구간은 0이었음. 이 결과는 동일 선택 결과의 재현성을 확인한 것이며 다른 계정·탐색 시드까지 품질이 동등하다는 뜻이 아님.

현재 `newSearch`만 켠 경로는 기존 방식 대비 클리어율 개선을 재현하지 못했음. 11/20 도구는 배치 확장도 함께 켰고 이전 정책 모듈을 사용했으므로 직접 같은 조건이라고 볼 수 없음. 운영 중인 현재 시즌도 검증하지 못했음. 이 조건 차이를 해소하기 전에는 `newSearch=false`를 유지하며 기본 전환 커밋을 만들지 않음. 계정별 점수·구간·실행 시간과 원문은 비공개 측정 폴더에 보관함.

실제 Pyodide의 변경 후 전체 탐색도 새 브라우저·재개 없음·워커 2개로 한 번 완료했음. 목표 시간 대비 비율은 0.7073이었음. 브라우저와 네이티브의 전투 결과·후보 경로는 서로 달랐으므로 네이티브 독립 평가를 브라우저 실측이라고 쓰지 않음.

기존 엔진 `Battle._roll_prio`는 `hash(st[:8])`에서 우선순위 난수 시드를 만듦(`battlesim/mc.py`). 같은 고정 합성 시드로 확인한 네이티브 Python과 Pyodide의 해시 폭은 64/32비트이고 우선순위 난수열도 달랐음. 이 경로가 플랫폼 간 동일 시드 재현성을 보장하지 않는 것은 확인했지만 모든 결과 차이의 유일한 원인이라고 단정하지 않음. 이번 작업에서는 엔진을 고치지 않았음.

패키지 manifest에는 길드 탐색 설정도 포함되므로 배분 설정만 바꿔도 해시가 바뀜. `test_search_executor.py`는 기존 골든 파일을 유지하면서 고정 커밋의 모든 엔진 입력 파일을 대조하고, 길드 파일의 탐색 설정과 설명만 비교에서 제외함. 전투 데이터·엔진 코드·파일 목록 변경은 거부하며 변이 시험으로 확인함.
